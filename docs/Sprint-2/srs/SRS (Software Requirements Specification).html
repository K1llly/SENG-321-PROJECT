1. Introduction

1.1 Purpose

This Software Requirements Specification (SRS) defines the complete functional requirements, role-based interactions, institution-specific business rules, and quality references for the Education Management System—a modular, API-first Student Information System (OBS) designed for language courses, tutoring centers, K–12 schools (primary, middle, and high schools), and universities. It serves as the single source of truth for the Architecture, Implementation, Quality Assurance (QA), and DevOps teams.

1.2 Scope and Scope Lock

The system is built on a fixed core (local authentication, user/institution management, and academic calendar) extended by independent business modules activated according to the selected institution type.

  • In-Scope: Institution Creation Tool / Setup Wizard (FR-SETUP), local username/password authentication & RBAC (FR-AUTH), classroom/section capacity & assignments (FR-CLS), daily attendance & absence cutoffs (FR-ATT), flexible exam weighting & report card/transcript engine (FR-GRD), hybrid auto-scheduling (FR-SCH), and reusable mock exam templates (FR-MOCK).
  • Out-of-Scope (Locked Out): Financial accounting and installment/invoicing modules, SMS/WhatsApp parent notification gateways, live online video-conferencing infrastructure, physical classroom maintenance, and external enterprise SSO/Identity Provider integrations.

1.3 Definitions and Acronyms

  • OBS: Student Information System (Öğrenci Bilgi Sistemi)
  • RBAC / JWT: Role-Based Access Control / JSON Web Token
  • MEB / ŞÖK: Ministry of National Education of Türkiye / Branch Teachers' Board (Şube Öğretmenler Kurulu)
  • ECTS (AKTS) / GPA / CGPA: European Credit Transfer System / Grade Point Average / Cumulative GPA

2. Overall Description

2.1 User Classes and Roles (RBAC)

  • Manager (MANAGER): Runs initial setup, configures classes/sections and capacities, assigns teachers and students, manages exam weights, mock templates, and hybrid timetables, and generates institutional report cards/transcripts.
  • Teacher (TEACHER): Records attendance, exam grades, and mock exam scores strictly for assigned classes; submits weekly availability preferences; approves or requests revisions on student course registration drafts in University mode.
  • Student (STUDENT): Views grades, attendance, timetables, mock exam analytics, and report cards in read-only mode (courses and K–12); creates add/drop course registration drafts in University mode.
  • Parent (PARENT — K–12 Schools Only): Monitors linked students' attendance, grades, developmental reports, mock exam results, and report cards in read-only mode.

2.2 Technical Constraints and Assumptions

  • Architecture & Stack: Node.js + Express + Prisma + PostgreSQL (Backend), React + Nginx (Frontend), OpenAPI 3.1 (API Contract), Docker & Docker Compose (Deployment), and GitHub Actions (CI/CD).
  • Authentication Assumption: Users authenticate locally via username and password stored in the system's PostgreSQL database without external SSO providers.
  • Licensing: Released under the open-source MIT License.

3. Functional Requirements

3.1 Institution Creation Tool / Setup Wizard (FR-SETUP)

  • FR-SETUP-01 (Institution Type Selection): During initial setup, the system shall allow the MANAGER to select the institution type: COURSES, PRIMARY_SCHOOL, MIDDLE_SCHOOL, HIGH_SCHOOL, or UNIVERSITY.
  • FR-SETUP-02 (Automatic Regulation & Pass/Fail Strategy): The system shall automatically activate the corresponding grading and pass/fail rule engine based on the selected institution type.
  • FR-SETUP-03 (Dynamic Module Activation): Incompatible modules (e.g., Parent Portal in tutoring centers or ECTS course selection in primary schools) shall be automatically disabled and hidden.
  • FR-SETUP-04 (Academic Calendar & Absence Limits): The wizard shall allow configuring term/level dates and institutional absence thresholds during setup.
  • FR-SETUP-05 (Dynamic Navigation Generation): Upon completing setup, role-based navigation menus shall render dynamically according to the active institution preset.

3.2 Local Authentication and Authorization (FR-AUTH)

  • FR-AUTH-01 (User Login): The /auth/login endpoint shall validate username/password credentials and issue a signed JWT containing the user's role.
  • FR-AUTH-02 (Invalid Credentials Handling): Invalid credentials shall be rejected with 401 Unauthorized.
  • FR-AUTH-03 (Role-Based Access Enforcement): Requests targeting resources outside a user's role or class assignment scope shall be rejected with 403 Forbidden.

3.3 Classroom, Capacity, and Assignment Management (FR-CLS)

  • FR-CLS-01 (Classroom/Section Creation): A MANAGER shall create classes, course groups, or school sections with a maximum student capacity.
  • FR-CLS-02 (Capacity Input Validation): Zero or negative capacities shall be rejected with 400 Bad Request.
  • FR-CLS-03 (Concurrency & Double-Booking Prevention): Student enrollment shall verify remaining capacity inside an atomic database transaction to prevent capacity overflow and concurrent double-booking.
  • FR-CLS-04 (Teacher & Student Assignment): Managers shall assign teachers and enroll students. In K–12 school modes, enrolling a student into a section shall automatically link all section curriculum courses and teachers to that student.

3.4 Attendance and Absence Tracking (FR-ATT)

  • FR-ATT-01 (Daily Attendance Entry): A TEACHER shall record Present, Absent, or Late statuses strictly for assigned classes and dates.
  • FR-ATT-02 (Excused vs. Unexcused Tracking — K–12): School administrators shall record excused/medical absences separately, maintaining distinct excused and unexcused day counters.
  • FR-ATT-03 (Automatic Attendance Cutoff): Exceeding the configured absence limit (e.g., 10 unexcused or 30 total days in High School) shall automatically flag the student as "Failed due to Absence" regardless of grade averages.

3.5 Flexible Exam, Grading, and Report Card / Transcript Engine (FR-GRD)

  • FR-GRD-01 (Exam Type & Weight Configuration): Managers/instructors shall define exam types (Written 1/2, Performance, or Midterm/Final/Lab/Makeup) and their percentage weights.
  • FR-GRD-02 (Grade Entry & Range Validation): Teachers shall enter scores between 0 and 100 strictly for assigned classes; out-of-range values shall return 400 Bad Request.
  • FR-GRD-03 (Weighted Average & Makeup Override): The system shall compute weighted averages automatically. In University mode, entering a Makeup (Bütünleme) score shall override the Final score and recalculate the course average.
  • FR-GRD-04 (Institution-Specific Pass/Fail Strategies):
    • Courses / Tutoring: Evaluates a single threshold (e.g., 70) for "Promoted / Failed".
    • Primary School (1–4): Hides numeric score inputs and generates a competency-based Developmental Report.
    • Middle School (5–8, MEB): Automatically routes students with Turkish < 70 or any other subject < 50 to the ŞÖK Decision List.
    • High School (9–12, MEB): Combines Term 1 and Term 2 averages to compute year-end GPA, direct/conditional pass status, and Honor/High Honor certificates.
    • University: Supports absolute or relative (curve) grading for letter grades (AA–FF), term GPA, and cumulative CGPA.
  • FR-GRD-05 (University Course Registration & Advisor Approval): Add/drop actions shall validate prerequisites, ECTS limits, time conflicts, and quotas sequentially; drafts require advisor approval and auto-lock when the registration window closes.

3.6 Hybrid and Automatic Weekly Scheduling (FR-SCH)

  • FR-SCH-01 (Teacher Availability): Teachers shall mark weekly grid slots as AVAILABLE, PREFER_NOT, or UNAVAILABLE.
  • FR-SCH-02 (Course Load & Block Splitting): Managers shall define weekly hours and block rules per section and course (e.g., 6 hours split as [3, 3] across 2 days).
  • FR-SCH-03 (Manual Pinning): Managers shall manually place and lock specific slots using isPinned: true.
  • FR-SCH-04 (Auto-Fill): Auto-Fill shall preserve pinned slots and distribute remaining course blocks into valid open slots.
  • FR-SCH-05 (Constraint Enforcement): The engine shall prevent teacher, section, and room conflicts, room capacity violations, UNAVAILABLE placements, and same-day stacking of split blocks.
  • FR-SCH-06 (Unplaced Reporting & Publishing): Unplaceable blocks shall be returned in a 200 OK response with reasons (e.g., INSUFFICIENT_TEACHER_AVAILABILITY). Setting status to PUBLISHED exposes the schedule in read-only mode to teachers and students.

3.7 Mock Exams and Reusable Templates (FR-MOCK)

  • FR-MOCK-01 (Template Management): Managers shall define reusable templates (MockExamTemplate), subject question counts (MockExamTemplateSection), and wrong-answer penalty ratios (wrongPenaltyRatio).
  • FR-MOCK-02 (Session & Grade Impact Lock): Managers shall launch sessions (MockExamSession) from templates. In COURSES mode, affectsFinalGrade and weightIfAffected are configurable; in K–12 school modes, affectsFinalGrade is strictly locked to false.
  • FR-MOCK-03 (Result Entry & Bounds Validation): Teachers shall enter correct and wrong counts per section. The API shall enforce correctCount + wrongCount <= questionCount (rejecting violations with 400 Bad Request).
  • FR-MOCK-04 (Automatic Blank & Net Calculation): The system shall compute blank counts and net scores (MockExamResult) automatically:
    blankCount = questionCount - (correctCount + wrongCount)
    netScore = (wrongPenaltyRatio > 0) ? correctCount - (wrongCount / wrongPenaltyRatio) : correctCount
  • FR-MOCK-05 (Separated Reporting): Student and parent portals shall show mock exam results in a separate read-only tab with historical trend comparisons across sessions of the same template.

6. Non-Functional Requirements & Quality Summary (Cross-Reference)

Detailed metrics and verification gates are maintained in [S2-05] Non-Functional Requirements (Reyhan Çetin) and [S2-06] Quality Measures & Test Strategy (Serhat Eroğlu). Core targets aligned with this SRS include:

  • Security: Passwords hashed with bcrypt; JWT authentication and RBAC (401/403) enforced on all protected routes.
  • Data Integrity & Concurrency: Capacity limits, schedule conflict checks, and concurrent enrollments protected via atomic PostgreSQL transactions.
  • Portability: Full stack (React, Node.js API, PostgreSQL) runs via a single docker compose up command.
  • Quality & Test Coverage: Minimum 50% unit test coverage (Jest/Vitest) on core business logic, SonarQube static analysis gates, and OpenAPI 3.1 contract compliance.
