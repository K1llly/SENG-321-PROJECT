1. Introduction

1.1 Purpose

This Software Requirements Specification (SRS) defines the complete functional requirements, role-based interactions, institution-specific business rules, and quality references for the Education Management System—a modular, API-first Student Information System (OBS) designed for language courses, tutoring centers, K–12 schools (primary, middle, and high schools), and universities. It serves as the single source of truth for the Architecture, Implementation, Quality Assurance (QA), and DevOps teams.

1.2 Scope and Scope Lock

The system is built on a fixed core (local authentication, user/institution management, and academic calendar) extended by independent business modules activated according to the selected institution type.

  • In-Scope: Institution Creation Tool / Setup Wizard (FR-SETUP), local username/password authentication & RBAC (FR-AUTH), classroom/section capacity & assignments (FR-CLS), daily attendance & absence cutoffs (FR-ATT), flexible exam weighting & report card/transcript engine (FR-GRD), hybrid auto-scheduling (FR-SCH), and reusable mock exam templates (FR-MOCK).
  • Out-of-Scope (Locked Out): Financial accounting and installment/invoicing modules, SMS/WhatsApp parent notification gateways, live online video-conferencing infrastructure, physical classroom maintenance, and external enterprise SSO/Identity Provider integrations.

1.4 Definitions and Acronyms

  • OBS: Student Information System (Öğrenci Bilgi Sistemi)
  • RBAC / JWT: Role-Based Access Control / JSON Web Token
  • MEB / ŞÖK: Ministry of National Education of Türkiye / Branch Teachers' Board (Şube Öğretmenler Kurulu)
  • ECTS (AKTS) / GPA / CGPA: European Credit Transfer System / Grade Point Average / Cumulative GPA

2. Overall Description

2.1 User Classes and Roles (RBAC)

  • Manager (MANAGER): Runs initial setup, configures classes/sections and capacities, assigns teachers and students, manages mock exam templates and hybrid timetables, and generates institutional report cards/transcripts. Exam weights belong to the teacher of the course (see FR-GRD-01).
  • Teacher (TEACHER): Defines the exam types and percentage weights of own courses, records attendance, exam grades, and mock exam scores strictly for assigned classes, submits weekly availability preferences, and approves or requests revisions on student course registration drafts in University mode.
  • Student (STUDENT): Views grades, attendance, timetables, mock exam analytics, and report cards in read-only mode (courses and K–12); creates add/drop course registration drafts in University mode.
  • Parent (PARENT — K–12 Schools Only): Monitors linked students' attendance, grades, developmental reports, mock exam results, and report cards in read-only mode.

2.2 Technical Constraints and Assumptions

  • Architecture & Stack: Node.js + Express + Prisma + PostgreSQL (Backend), React + Nginx (Frontend), OpenAPI 3.1 (API Contract), Docker & Docker Compose (Deployment), and GitHub Actions (CI/CD).
  • Authentication Assumption: Users authenticate locally via username and password stored in the system's PostgreSQL database without external SSO providers.
  • Licensing: Released under the open-source MIT License.

3. Functional Requirements

3.1 Institution Creation Tool / Setup Wizard (FR-SETUP)

  • FR-SETUP-01 (Institution Type Selection): During initial setup, the system shall allow the MANAGER to select the institution type: COURSES, PRIMARY_SCHOOL, MIDDLE_SCHOOL, HIGH_SCHOOL, or UNIVERSITY.
  • FR-SETUP-02 (Automatic Regulation & Pass/Fail Strategy): The system shall automatically activate the corresponding grading and pass/fail rule engine based on the selected institution type.
  • FR-SETUP-03 (Dynamic Module Activation): Incompatible modules (e.g., Parent Portal in tutoring centers or ECTS course selection in primary schools) shall be automatically disabled and hidden.
  • FR-SETUP-04 (Academic Calendar & Absence Limits): The wizard shall allow configuring term/level dates and institutional absence thresholds during setup.
  • FR-SETUP-05 (Dynamic Navigation Generation): Upon completing setup, role-based navigation menus shall render dynamically according to the active institution preset.

3.2 Local Authentication and Authorization (FR-AUTH)

  • FR-AUTH-01 (User Login): The /auth/login endpoint shall validate username/password credentials and issue a signed JWT containing the user's role.
  • FR-AUTH-02 (Invalid Credentials Handling): Invalid credentials shall be rejected with 401 Unauthorized.
  • FR-AUTH-03 (Role-Based Access Enforcement): Requests targeting resources outside a user's role or class assignment scope shall be rejected with 403 Forbidden.

3.3 Classroom, Capacity, and Assignment Management (FR-CLS)

  • FR-CLS-01 (Classroom/Section Creation): A MANAGER shall create classes, course groups, or school sections with a maximum student capacity.
  • FR-CLS-02 (Capacity Input Validation): Zero or negative capacities shall be rejected with 400 Bad Request.
  • FR-CLS-03 (Concurrency & Double-Booking Prevention): Student enrollment shall verify remaining capacity inside an atomic database transaction to prevent capacity overflow and concurrent double-booking.
  • FR-CLS-04 (Teacher & Student Assignment): Managers shall assign teachers and enroll students. In K–12 school modes, enrolling a student into a section shall automatically link all section curriculum courses and teachers to that student.

3.4 Attendance and Absence Tracking (FR-ATT)

  • FR-ATT-01 (Daily Attendance Entry): A TEACHER shall record Present, Absent, or Late statuses strictly for assigned classes and dates.
  • FR-ATT-02 (Excused vs. Unexcused Tracking — K–12): School administrators shall record excused/medical absences separately, maintaining distinct excused and unexcused day counters.
  • FR-ATT-03 (Automatic Attendance Cutoff): Exceeding the configured absence limit (e.g., 10 unexcused or 30 total days in High School) shall automatically flag the student as "Failed due to Absence" regardless of grade averages.

3.5 Flexible Exam, Grading, and Report Card / Transcript Engine (FR-GRD)

  • FR-GRD-01 (Exam Type & Weight Configuration): The TEACHER assigned to a course shall define its exam types (Written 1/2, Performance, or Midterm/Final/Lab/Makeup) and their percentage weights. The weights of the active exam types of a course shall sum to 100%; a configuration that does not is rejected. The manager may review the configuration but does not own it.
  • FR-GRD-02 (Grade Entry & Range Validation): Teachers shall enter scores between 0 and 100 strictly for assigned classes; out-of-range values shall return 400 Bad Request.
  • FR-GRD-03 (Weighted Average & Makeup Override): The system shall compute weighted averages automatically. In University mode, entering a Makeup (Bütünleme) score shall override the Final score and recalculate the course average.
  • FR-GRD-04 (Institution-Specific Pass/Fail Strategies):
    • Courses / Tutoring: Evaluates a single threshold (e.g., 70) for "Promoted / Failed".
    • Primary School (1–4): Hides numeric score inputs and generates a competency-based Developmental Report.
    • Middle School (5–8, MEB): Automatically routes students with Turkish < 70 or any other subject < 50 to the ŞÖK Decision List.
    • High School (9–12, MEB): Combines Term 1 and Term 2 averages to compute year-end GPA, direct/conditional pass status, and Honor/High Honor certificates.
    • University: Supports absolute or relative (curve) grading for letter grades (AA–FF), term GPA, and cumulative CGPA.
  • FR-GRD-05 (University Course Registration & Advisor Approval): Add/drop actions shall validate prerequisites, ECTS limits, time conflicts, and quotas sequentially; drafts require advisor approval and auto-lock when the registration window closes.

3.6 Hybrid and Automatic Weekly Scheduling (FR-SCH)

  • FR-SCH-01 (Teacher Availability): Teachers shall mark weekly grid slots as AVAILABLE, PREFER_NOT, or UNAVAILABLE.
  • FR-SCH-02 (Course Load & Block Splitting): Managers shall define weekly hours and block rules per section and course (e.g., 6 hours split as [3, 3] across 2 days).
  • FR-SCH-03 (Manual Pinning): Managers shall manually place and lock specific slots using isPinned: true.
  • FR-SCH-04 (Auto-Fill): Auto-Fill shall preserve pinned slots and distribute remaining course blocks into valid open slots.
  • FR-SCH-05 (Constraint Enforcement): The engine shall prevent teacher, section, and room conflicts, room capacity violations, UNAVAILABLE placements, and same-day stacking of split blocks.
  • FR-SCH-06 (Unplaced Reporting & Publishing): Unplaceable blocks shall be returned in a 200 OK response with reasons (e.g., INSUFFICIENT_TEACHER_AVAILABILITY). Setting status to PUBLISHED exposes the schedule in read-only mode to teachers and students.

3.7 Mock Exams and Reusable Templates (FR-MOCK)

  • FR-MOCK-01 (Template Management): Managers shall define reusable templates (MockExamTemplate), subject question counts (MockExamTemplateSection), and wrong-answer penalty ratios (wrongPenaltyRatio).
  • FR-MOCK-02 (Session & Grade Impact Lock): Managers shall launch sessions (MockExamSession) from templates. In COURSES mode, affectsFinalGrade and weightIfAffected are configurable; in K–12 school modes, affectsFinalGrade is strictly locked to false.
  • FR-MOCK-03 (Result Entry & Bounds Validation): Teachers shall enter correct and wrong counts per section. The API shall enforce correctCount + wrongCount <= questionCount (rejecting violations with 400 Bad Request).
  • FR-MOCK-04 (Automatic Blank & Net Calculation): The system shall compute blank counts and net scores (MockExamResult) automatically:
    blankCount = questionCount - (correctCount + wrongCount)
    netScore = (wrongPenaltyRatio > 0) ? correctCount - (wrongCount / wrongPenaltyRatio) : correctCount
  • FR-MOCK-05 (Separated Reporting): Student and parent portals shall show mock exam results in a separate read-only tab with historical trend comparisons across sessions of the same template.

4. User Stories and Acceptance Criteria

This section restates the backlog items of the traceability matrix (Section 6) as user stories in the standard “As a … I want … so that …” form and attaches the acceptance criteria that will be used to verify each story during implementation and Sprint review. Every acceptance criterion is derived from, and traceable to, the numbered functional requirements in Section 3. A story is considered Done only when all of its acceptance criteria are met.

US-01 — Local User Authentication (Login & RBAC)

Primary role: all roles (MANAGER, TEACHER, STUDENT, PARENT) · Requirements: FR-AUTH-01 – FR-AUTH-03 · Priority: High · Effort: 3 SP

As a registered user of the institution, I want to sign in with my username and password so that I can access exactly the functions and data my role is allowed to see.

Acceptance criteria

  • AC-01.1 Given a registered username and the correct password, when the user submits the login form, then POST /auth/login returns 200 OK with a signed JWT that carries the user's identifier and role, and the user is routed to the menu of that role.
  • AC-01.2 Given a wrong password or an unknown username, when the user submits the login form, then the API returns 401 Unauthorized, no token is issued, and the response does not reveal which of the two values was incorrect.
  • AC-01.3 Passwords are persisted only as bcrypt hashes; no plaintext or hash is ever returned by an API response or written to the logs.
  • AC-01.4 When a protected endpoint is called without a token, with an expired token, or with a tampered token, then the API returns 401 Unauthorized.
  • AC-01.5 When an authenticated user requests a resource outside their role or class assignment (for example, a TEACHER opening a section that is not assigned to them, or a STUDENT calling a grade-entry endpoint), then the API returns 403 Forbidden and no data is disclosed.
  • AC-01.6 After login, the rendered navigation contains only the modules that the Section 5 visibility matrix marks as active for the user's role and institution type.

US-02 — Classroom / Section & Capacity Management

Primary role: MANAGER · Requirements: FR-CLS-01 – FR-CLS-04 · Priority: Medium · Effort: 5 SP

As a Manager, I want to create classes/sections with a maximum capacity and assign the teachers and students of each one so that the academic structure of the institution is modelled accurately and can never be overbooked.

Acceptance criteria

  • AC-02.1 Given a Manager session, when the Manager creates a class/section (or course group) with a name and a maximum capacity, then the section is persisted and listed with its current occupancy and remaining capacity.
  • AC-02.2 When a capacity of 0 or a negative value is submitted, then the API returns 400 Bad Request and no section is created.
  • AC-02.3 When two enrollments for the last free seat of a section are submitted at the same time, then exactly one succeeds and the section's enrollment count never exceeds its configured capacity; the capacity check and the insert run inside a single atomic database transaction.
  • AC-02.4 When the Manager assigns a teacher to a section or enrolls a student, then only existing, active users of the matching role can be selected, and the assignment is reflected in the teacher's and the student's own views.
  • AC-02.5 In K–12 institution modes, when a student is enrolled in a section, then all curriculum courses and teachers of that section are automatically linked to the student without a second manual step.

US-03 — Exam Grade Entry, Attendance & Weighting

Primary role: TEACHER · Requirements: FR-ATT-01 – FR-ATT-03, FR-GRD-01 – FR-GRD-02 · Priority: High · Effort: 8 SP

As a Teacher, I want to record daily attendance and exam scores for my assigned classes, using the exam weights configured by my institution, so that every student's progress is captured consistently and can later be turned into a legally correct report card.

Acceptance criteria

  • AC-03.1 Given a Teacher assigned to a class, when the Teacher records attendance for a date, then each student receives exactly one status of Present, Absent, or Late for that date, and re-entering the same date updates the existing record instead of duplicating it.
  • AC-03.2 When a Teacher tries to record attendance or grades for a class or date that is not assigned to them, then the API returns 403 Forbidden and nothing is stored.
  • AC-03.3 In K–12 modes, when a school administrator marks an absence as excused/medical, then the excused and unexcused day counters of the student are incremented separately and both remain visible.
  • AC-03.4 When a student's excused/unexcused or total absence days exceed the threshold configured for the institution type (for example 10 unexcused or 30 total days in High School), then the student is automatically flagged as Failed due to Absence regardless of the grade average.
  • AC-03.5 Given a course assigned to a Teacher, when that Teacher defines the exam types and their percentage weights, then the configuration is persisted per course/section and is the set used for grade entry and for the weighted average; a Teacher cannot configure a course that is not assigned to them (403).
  • AC-03.6 When a score outside the 0–100 range (including non-numeric input) is submitted, then the API returns 400 Bad Request and the previously stored score is left unchanged.
  • AC-03.7 When a valid score is accepted, then it is stored against the correct student, exam type, and section, and the weighted average of that student is recalculated immediately.

US-04 — Weighted Average & Report Card / Transcript Engine

Primary roles: MANAGER (generation), STUDENT / PARENT (read-only) · Requirements: FR-GRD-03 – FR-GRD-05 · Priority: High · Effort: 8 SP

As a Student (and, in K–12, as the Parent of a student), I want my weighted averages, report card, or transcript to be computed automatically according to the rules of my institution type so that I always see an accurate and explainable academic standing.

Acceptance criteria

  • AC-04.1 The course average equals the sum of (score × weight) over all exam types with at least one entered score, divided by the sum of the weights of those exam types, and it is recomputed whenever a score or a weight changes.
  • AC-04.2 In University mode, when a Makeup (Bütünleme) score is entered, then it replaces the Final score in the calculation and the course average and letter grade are recalculated.
  • AC-04.3 The pass/fail decision follows the strategy of the selected institution type: a single threshold in Courses/Tutoring mode; a competency-based Developmental Report with no numeric score in Primary School; a ŞÖK decision list for students with Turkish < 70 or any other subject < 50 in Middle School; Term 1 + Term 2 year-end GPA with direct/conditional pass and Honor/High Honor certificates in High School; absolute or curve letter grades (AA–FF) with term GPA and cumulative CGPA in University mode.
  • AC-04.4 When a report card or transcript is opened, then every displayed average can be traced back to its component scores and weights, and the document shows the institution name, the student, the term, and the generation date.
  • AC-04.5 STUDENT and PARENT accounts can only read report cards/transcripts and cannot create, edit, or regenerate them; MANAGER accounts can generate institutional report cards for the whole institution.
  • AC-04.6 In University mode, when a student submits an add/drop draft, then prerequisites, ECTS limits, time conflicts, and quotas are validated in that order and every violation is reported with its specific reason; a draft stays pending until the assigned advisor approves it.
  • AC-04.7 When the course-registration window closes, then all pending drafts are locked automatically and the student can no longer modify them.

US-05 — Hybrid & Automatic Weekly Scheduling

Primary role: MANAGER (build/publish), TEACHER (availability), all roles (read-only) · Requirements: FR-SCH-01 – FR-SCH-06 · Priority: High · Effort: 8 SP

As a Manager, I want to build the weekly timetable from teacher availability and course block rules, with an option to auto-fill the remaining slots so that a conflict-free schedule can be published in minutes instead of being assembled by hand.

Acceptance criteria

  • AC-05.1 A Teacher can mark each slot of the weekly grid as AVAILABLE, PREFER_NOT, or UNAVAILABLE, and the saved preferences are visible to the Manager before scheduling.
  • AC-05.2 A Manager can define the weekly hours and the block-splitting rule per section and course (for example 6 hours split as [3, 3] across two days), and the engine only produces blocks that match the configured split.
  • AC-05.3 A Manager can place a lesson manually and lock it; the locked slot is stored with isPinned: true and is never moved by Auto-Fill.
  • AC-05.4 When Auto-Fill is executed, then all pinned slots are preserved and the remaining blocks are distributed into valid open slots, or reported as unplaceable.
  • AC-05.5 The engine rejects any placement that would create a teacher, section, or room conflict, exceed room capacity, fall on an UNAVAILABLE teacher slot, or put two parts of the same split block on the same day.
  • AC-05.6 When a block cannot be placed, then the response is still 200 OK and lists the block together with a machine-readable reason (for example INSUFFICIENT_TEACHER_AVAILABILITY).
  • AC-05.7 When the Manager sets the schedule status to PUBLISHED, then teachers and students see the timetable in read-only mode and cannot modify it; before publication it is visible only to the Manager.

US-06 — Institution Creation Tool / Setup Wizard

Primary role: MANAGER · Requirements: FR-SETUP-01 – FR-SETUP-05 · Priority: High · Effort: 8 SP

As a Manager, I want to configure my institution once through a guided setup so that the system activates exactly the rules, modules, and menus that fit my institution type and nothing that does not apply to it.

Acceptance criteria

  • AC-06.1 Given a fresh installation, when the Manager runs the wizard, then the institution type can be selected from COURSES, PRIMARY_SCHOOL, MIDDLE_SCHOOL, HIGH_SCHOOL, or UNIVERSITY.
  • AC-06.2 When an institution type is selected, then the matching grading, pass/fail, and absence rule engine is activated automatically without further configuration.
  • AC-06.3 After setup, modules that are incompatible with the selected type (for example the Parent Portal in a tutoring centre or ECTS course selection in a primary school) are disabled both in the API and in the navigation.
  • AC-06.4 During setup the Manager can enter term/level dates and the institutional absence thresholds, and the values are persisted and used by the attendance module.
  • AC-06.5 When setup is completed, the role-based navigation is generated dynamically from the active institution preset for every subsequent login, and the wizard is not shown again.

US-07 — Mock Exam & Reusable Template Module

Primary roles: MANAGER (templates), TEACHER (results), STUDENT / PARENT (read-only) · Requirements: FR-MOCK-01 – FR-MOCK-05 · Priority: Medium · Effort: 5 SP

As a Manager, I want to define reusable mock exam templates and launch sessions from them, and as a Student or Parent, I want to follow the resulting net scores over time so that exam readiness can be tracked without touching official grades.

Acceptance criteria

  • AC-07.1 A Manager can create a template (MockExamTemplate) with one or more sections (MockExamTemplateSection) that define the question count per subject and a wrongPenaltyRatio.
  • AC-07.2 A Manager can launch a session (MockExamSession) from a template; in COURSES mode affectsFinalGrade and weightIfAffected are configurable, while in K–12 modes affectsFinalGrade is forced to false and cannot be changed.
  • AC-07.3 A Teacher can enter correctCount and wrongCount per section; when correctCount + wrongCount exceeds the section's questionCount, the API returns 400 Bad Request and stores nothing.
  • AC-07.4 After valid result entry the system computes and stores the blank count and the net score as blankCount = questionCount − (correctCount + wrongCount) and netScore = correctCount − (wrongCount / wrongPenaltyRatio) when wrongPenaltyRatio > 0, otherwise netScore = correctCount.
  • AC-07.5 Students and Parents see mock exam results in a separate read-only tab that compares the current net score with the previous sessions of the same template, and this tab never mixes mock results with official course grades.

7. Non-Functional Requirements & Quality Summary (Cross-Reference)

Detailed metrics and verification gates are maintained in [S2-05] Non-Functional Requirements (Reyhan Çetin) and [S2-06] Quality Measures & Test Strategy (Serhat Eroğlu). Core targets aligned with this SRS include:

  • Security: Passwords hashed with bcrypt; JWT authentication and RBAC (401/403) enforced on all protected routes.
  • Data Integrity & Concurrency: Capacity limits, schedule conflict checks, and concurrent enrollments protected via atomic PostgreSQL transactions.
  • Portability: Full stack (React, Node.js API, PostgreSQL) runs via a single docker compose up command.
  • Quality & Test Coverage: Minimum 50% unit test coverage (Jest/Vitest) on core business logic, SonarQube static analysis gates, and OpenAPI 3.1 contract compliance.
